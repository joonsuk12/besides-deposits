## 2026-11-11 — 프로젝트 시작

### 배경
- 자산관리 대화를 여러 환경에서 이어가려고 private 레포 `asset-management`를 만들었다.
- 그 과정에서 예전 팀 프로젝트 NewStocks/NewStocks를 로컬에서 띄워 써 볼까 검토했다.

### NewStocks 분석 결과
- 구성: Spring Boot 3.1(Java 17, 8200) + Next.js 13.4 + Flask 서버 3개(pykrx 주가 수집, 국내 뉴스 크롤링·BERT 감성분석·DBSCAN 군집화, 해외 뉴스 Selenium 크롤링) + 챗봇 서버(LangChain·FAISS) + MySQL(AWS RDS).
- 그대로 띄우기 어려운 이유: `.env` 없음, 운영 DB 내려갔을 가능성, 프론트가 운영 주소 고정, 로그인이 카카오·구글 OAuth뿐, 라이브러리 노후, PC에 Java·MySQL·Docker 없음.
- 공개 레포 `server/DomesticNews/app/app.py`에 DB 계정·비밀번호가 평문으로 남아 있음 (정리 필요, 미완료).

### 결정
1. **NewStocks를 띄우지 않고 가볍게 새로 만든다.** 가져올 것은 "차트 위에 뉴스 표시" 기능과 pykrx 수집·뉴스 처리 아이디어.
2. **백엔드는 FastAPI.** 사용자는 Spring 개발자라 코드를 이해할 수 있을지 걱정했다 → Spring식 계층 구조로 짜고, 파일마다 대응 주석을 달고, 흐름을 설명하며 진행하기로 했다. Django는 숨은 관례가 많아 제외.
3. **코드 레포를 자산 기록 레포와 분리한다.** 이유: 금융정보 보호, Claude 맥락 분리, 커밋 기록 분리, 코드 부속 파일 분리.
4. **기능 범위**: 차트 + 뉴스(관심 종목) + 증권사 리포트 요약(가급적 전체) + 공시. 사용자가 주식 초보이므로 리포트는 "초보가 어디를 봐야 하는지" 기준으로 틀에 맞춰 요약한다.
5. **리포트 요약은 2단계**: 전체 리포트는 간단 요약, 관심 종목과 직접 고른 리포트는 상세 요약. 결과는 DB에 저장.
6. **레포 이름** `stock-newbie-stroll`(주식초보나들이), private.
7. **첫 관심 종목**: 삼성전자, SK하이닉스, 두산, 펨트론.
8. **화면은 처음부터 Next.js.** 처음엔 Jinja2 템플릿(Thymeleaf와 비슷)을 추천했으나, 화면이 앱 수준으로 커질 것이라는 사용자 의견에 따라 변경. 백엔드는 JSON API만 담당.
9. **추가 요금 없이 구현한다.** 무료 데이터 출처, 로컬 실행, 유료 LLM API 미사용. 요약은 사용자의 Claude 구독 안에서 Claude Code 예약 작업으로 처리하는 방식을 기본안으로 한다 (3단계에서 구체화).
10. **개발 환경**: Windows 11, Python 3.12, Node.js 22 (기존 3.9 / 16에서 추가 설치).

## 2026-11-12 — 리포트 분석 요약·뉴스 키포인트

사용자 요청: "네이버 리서치의 분석 요약, 뉴스의 키포인트 집어내는 걸 중점적으로".

### 데이터 출처 결정
- 네이버 금융이 개편되어 리서치 목록 HTML이 비어 있고, 데이터는 네이버 증권 **내부 API**로만 온다.
- 공식 API(네이버 검색 API, OpenDART)와 내부 API의 차이를 설명했고, 사용자가 **개인용·저빈도 조건으로 내부 API 사용을 허용**했다.
- Claude Code 자동 모드의 권한 검사가 내부 API 호출과 권한 설정 수정을 막아서, 사용자가 권한 모드를 "승인 요청" 방식으로 바꾼 뒤 진행했다.
- 사용 중인 주소: 리포트 `stock.naver.com/api/stockSecurity/researches/v2/company?index&size(≤50)&startDate&endDate`, 종목별 `.../company/by-items?itemCodes&size(≤10)`, 뉴스 `stock.naver.com/api/domestic/detail/news?itemCode&page&pageSize`. 확인용 스크립트: `backend/scripts/probe_naver_research.py`.
- 요청 간격 0.5초, 같은 데이터는 30분(오늘 리포트·뉴스)~3시간(종목별 리포트) 안에 다시 요청하지 않는다. 지난 날짜 리포트는 한 번만 받는다.

### 키포인트 규칙 (유료 AI 없이)
- 리포트: 증권사 요약문의 굵은 소제목 = 한 줄 결론 (영어 꼬리표면 제목 사용), 숫자·판단어 점수 상위 3문장 = 핵심 근거, 우려·부진 같은 말이 긍정어보다 많은 문장 = 조심할 점, 용어사전 46개 중 나온 것 = 용어 풀이, 같은 증권사 직전 리포트와 비교한 목표주가 상향/하향/유지, 최근 종가와 목표주가 차이(%).
- 뉴스: 네이버가 묶어 준 기사 수 = 중요도("기사 N건"), 미리보기 첫 문장 = 한 줄 요약, 긍정·부정 단어 수로 분위기 추정("추정"으로 표시), 실적·수주 등 주제 꼬리표.

### 화면
- 새 화면 `오늘의 리포트`(/reports): 날짜 이동, 필터(관심종목·목표가 상향·하향·의견 없음), 검색. 카드에서 "자세히"로 근거·리스크·용어를 펼침.
- 차트: 리포트 나온 날 R, 뉴스 있는 날 N 표시 (NewStocks와 같은 방식). 날짜를 누르면 그날 리포트·뉴스가 오른쪽에. 아래에 "이번 주 많이 다뤄진 뉴스"와 최근 뉴스.
- 관심종목: 종목마다 최신 리포트 요약 + 이번 주 주요 뉴스 3건.

### 알아둘 점
- 뉴스는 종목당 최근 약 40묶음만 받아서 차트의 N 표시는 최근 날짜에만 있다. 앞으로 열어 볼 때마다 쌓인다.
- 리포트 목표주가 비교는 저장된 60일 안에서만 된다. 그 전 리포트가 없으면 표시하지 않는다.

## 2026-11-13 — '쉽게 말하면' 요약 (브랜치 feature/easy-summary)

### 방식
- Claude API는 사용량만큼 요금이 붙어서(가장 싼 모델도 유료) 쓰지 않는다. **Claude Code가 직접 요약을 쓴다** — 사용자의 구독 안에서 돌아가므로 추가 요금 없음.
- 흐름: `easy_cli pending`(오늘 리포트 수집 → 요약 없는 리포트를 관심 종목 먼저 JSON으로 내보냄) → Claude가 지침대로 작성 → `easy_cli save`(검증 후 DB 저장). 서버가 꺼져 있어도 되도록 CLI로 DB에 직접 접근한다. 같은 기능을 API로도 열어 둠: `GET /reports/easy/pending`, `POST /reports/easy`.
- 저장: 별도 테이블 `report_easy`(nid, one_liner, story, watch_out, written_by, written_at). 리포트 응답에 `easy` 필드로 붙는다.
- 작성 규칙: [docs/easy-summary-guide.md](easy-summary-guide.md) — 해요체, 용어는 괄호로 풀이, 원문에 있는 사실·숫자만, 매수·매도 권유 금지, 목표주가는 증권사 예상임을 분명히.

## 2026-11-14 — 4단계 공시 (OpenDART)

- 공시는 공식·무료 OpenDART API로 받는다. 키는 `backend/.env`의 `DART_API_KEY` (커밋하지 않음). 키가 없으면 화면에 안내 문구만 나온다.
- 처음 한 번 `corpCode.xml`로 종목코드↔DART 회사번호 대응표를 받고, 종목마다 처음엔 1년치, 이후엔 6시간마다 최근 2주치만 다시 받는다.
- 분류는 유료 AI 없이 **공시 이름 규칙**(`disclosure/keypoints.py`)으로 한다. 위에서부터 처음 맞는 규칙 하나. 색: 확인 필요(warn)·주주에게 좋은 쪽(good)·중요(key)·참고(info).
- 실데이터(관심 4종목 3,514건)로 확인 후 고친 점: "동일인등출자계열회사와의…거래"가 '출자' 때문에 다른 회사 투자로 잡히던 것을 **계열사 거래**로, 풍문·조회공시 답변을 **소문 해명**으로, 중대재해·파생상품 손실을 **확인 필요**로, 기업가치제고계획·대표이사 변경·유형자산 취득·투자판단 주요경영사항을 **중요**로 분류.
- 삼성전자는 임원·주요주주 지분 보고가 대부분(1년 3,000건 넘음)이라 화면에서는 참고용을 접어 두고 중요한 것부터 보여 준다. 차트 D 표시도 참고용은 빼고 단다.
- 매일 수집은 서버와 상관없이 `python -m app.daily`(레포의 `daily_collect.cmd`)로 돈다. 단계마다 실패해도 다음 단계는 계속한다.

## 2026-11-14 — PER·PBR과 업종 비교

- 재료(EPS·BPS)는 네이버 증권 모바일 내부 API `m.stock.naver.com/api/stock/{code}/integration`에서 받는다 (무료, 개인용·저빈도 허용 범위). 반나절(720분)에 한 번만 다시 받는다.
- PER = 우리 DB의 최근 종가 ÷ EPS, PBR = 최근 종가 ÷ BPS로 **직접 계산**한다. EPS가 0 이하(적자)면 PER은 계산하지 않는다.
- "업종 평균"은 네이버가 고른 같은 업종 주요 회사 5~6곳(`industryCompareInfo`)의 **중간값**으로 한다.
  - 업종 전체(반도체는 174곳)를 다 부르는 건 요청이 너무 많아 하지 않았다.
  - 평균 대신 중간값: 이익이 아주 적은 회사 하나가 PER 1,000배가 넘게 나와 평균을 망가뜨린다(예: 주성엔지니어링 1,131배).
  - 적자 회사와 값이 없는 회사는 빼고, 남은 회사가 2곳 미만이면 비교하지 않는다.
- 문구: 업종과 ±15% 안이면 "비슷", 100% 넘게 높으면 "%" 대신 "약 N배". PER이 100배 이상이면 "이익이 아주 적어서 PER이 크게 나와요" 안내를 붙인다.
- 매수·매도 권유가 되지 않게 "싸다/비싸다" 대신 "이익(순자산)에 비해 주가가 낮게/높게 매겨진 편"이라고 쓰고, 낮고 높음의 뜻이 하나가 아니라는 안내를 항상 붙인다. 색도 등락 색(빨강·파랑) 대신 중립 색을 쓴다.
- 화면: 차트 오른쪽 "💰 주가 수준" 카드(계산식, 추정 PER, 비교 회사 표 포함), 관심종목은 간단 버전.

## 2026-11-14 — 화면 정보량 줄이기 (사용자 요청)

- 이유: 한 화면에 뉴스·공시·리포트를 너무 많이 보여주면 초보가 정보의 바다에서 헤맨다.
- 원칙: **각 목록은 3개만 먼저 보여주고 나머지는 "N건 더 보기"** (`components/ShowMore`). 날짜를 바꾸면 다시 접힌다.
- 차트 화면
  - "이번 주 많이 다뤄진 뉴스"는 3개만. "최근 뉴스" 칸은 없앴다.
  - 날짜를 누르면 나오는 뉴스는 "이날의 주요 뉴스"로 이름을 바꾸고, 기사가 많이 겹친(여러 언론사가 다룬) 순서로.
  - 공시는 중요한 순서(확인 필요 → 주주에게 좋은 쪽 → 중요 → 참고, 같으면 최신순)로 3개.
  - "최근 공시"와 관심종목 공시는 참고용(정기 보고서·임원 지분 보고)을 아예 빼고 "N건은 뺐어요"라고만 적는다. 삼성전자는 1년에 2,800건이 넘어 "더 보기"로도 감당이 안 된다. 그날 공시 목록에는 참고용도 남긴다.
  - 증권사 리포트는 최신 3개.
- 관심종목 화면은 원래 리포트 1개·뉴스 3개라 그대로 두고, 공시만 위 규칙을 따른다.

## 2026-11-14 — 업종별로 PER·PBR 중 무엇을 더 볼지

- 업종 이름 규칙(`valuation/focus.py`)으로 정한다. 위에서부터 처음 맞는 규칙 하나.
  - 금융(은행·증권·보험 등), 지주회사(복합기업), 경기 민감 업종(철강·화학·조선·해운·건설 등) → **PBR**
  - 반도체·디스플레이 → **둘 다** (업황에 따라 이익이 크게 변함. 불황엔 PBR, 호황엔 PER·추정 PER)
  - 바이오·제약 → **둘 다 잘 안 맞음** (적자가 흔함, 임상·기술 수출 소식이 더 중요)
  - 소프트웨어·인터넷·게임·화장품·식품·유통 등 → **PER** (자산보다 브랜드·기술로 버는 업종)
  - 그 밖 → PER 먼저, PBR 함께 참고. 적자 회사는 업종과 상관없이 PBR(바이오 제외).
- 화면: 주가 수준 카드 맨 위에 "👉 ○○ 업종은 PBR을 주로 봐요" + 이유, 해당 지표 옆에 ★. 관심종목 화면은 제목만.

## 2026-11-16 — 공시: 좋은/나쁜 소식 구분, 자세히·원문 (사용자 요청)

- 공시 카드에 꼬리표: "👍 좋은 소식 (보통)" / "⚠️ 나쁜 소식 (보통)" / "🔎 중요 · 내용을 봐야 알아요". 참고용은 꼬리표 없음.
  공시 이름만 보고 붙이므로 "(보통)" 단서를 단다. 색은 뉴스와 같이 좋은 쪽 빨강, 나쁜 쪽 파랑 + 카드 왼쪽 색 띠.
- 리포트 카드처럼 "자세히"와 "원문 ↗". 자세히 = **왜 그렇게 보나요** + **원문에서 확인할 것** 목록.
  내용은 `disclosure/keypoints.py`의 `DETAILS`(분류 이름 → 설명) 26개. API에 `why`, `checks` 추가.
- 규칙 보강: 계약 해지·전환가격 조정(리픽싱)·회생/파산·영업정지·벌금 → 나쁜 소식, 공개매수·유상감자 → 중요,
  사채 만기 전 취득·자사주 신탁 종료·주식 분할/병합 → 참고, 무상증자는 참고 → 좋은 소식.
- 실적 발표·실적 30% 변화는 이름만으로 좋고 나쁨을 알 수 없어 "내용을 봐야 알아요"로 둔다 (원문 숫자를 읽어야 함. OpenDART 목록 API는 이름만 준다).
- 알아둘 점: "최근 공시" 3개는 등급 순(나쁜 → 좋은 → 중요)이라 몇 달 전 나쁜 소식이 최근 좋은 소식보다 위에 올 수 있다.
- 실행 메모: 이 PC의 PowerShell은 실행 정책 때문에 `npm run dev`가 막힌다. `npm.cmd run dev`로 실행한다.
